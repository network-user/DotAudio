## Что уже лежит в проекте

| Компонент | Что есть | Чего это пока не доказывает |
|---|---|---|
| Python-пакет | pyproject, entrypoints, отдельная `.venv` | Нет проверенного установщика и lock-файла |
| Engine | faster-whisper, CPU/GPU, кеш одной модели, local/remote | `tiny` CPU прошёл реальный inference на тестовом буфере; нет замеров качества речи |
| Capture | sounddevice, soundcard loopback, FFmpeg HTTP-поток | Устройства перечисляются; открытие микрофона зависит от драйвера и разрешений Windows |
| Live pipeline | разделение по энергии/тишине, очередь, отмена, тесты хвоста/отмены | Нет стабилизации частичных гипотез и качественных бесшовных границ |
| SQLite | сессии, сегменты, исходный/правленый текст, настройки, поиск | Нет миграций и recovery после аварии |
| Экспорт | TXT/SRT/VTT/JSON, ключевые слова | Семантического поиска новостей нет |
| Qt | страницы режимов, остров, плеер, редактор сегментов, журнал мониторинга | Визуальная проверка сделана в offscreen; нужны реальные DPI/экран/доступность |
| Windows | глобальные Ctrl+Alt+Space / Ctrl+Alt+O, clipboard/Ctrl+V | Вставка в реальные приложения и поведение фокуса не проверялись |
| Server | FastAPI upload, limits, busy, cancel, CPU Docker-конфигурация | Docker не собирался; публичного сервиса, GPU-деплоя и Timeweb нет |

В QML есть видеоплеер, список редактируемых сегментов и журнал совпадений. Менеджер загрузок моделей, tray, глобальный Escape, переназначение hotkeys, восстановление связи с эфиром и semantic search остаются следующими итерациями.

## Приоритетный технический разбор до наращивания функций

1. `pipeline.py` / `capture.py`: гонки start/stop/cancel и draining хвоста записи; повторное завершение; остановка dispatcher из callback; переполнение нижней очереди сейчас может вытеснять события. Нужны тесты и явный backpressure, чтобы не терять аудио незаметно.
2. `engine.py`: получение модели и eviction относительно общего inference lock; fallback после уже выданных GPU-сегментов; время ожидания отмены при загрузке модели/сетевом чтении. Это точки для проверки, не подтверждённые production-гарантии.
3. `controller.py`: `_jobs`/сигналы между потоками, повторное jobFinished при неудачном startup, сообщения ошибок, блокирующие обращения к SQLite, разрастание списка сегментов. Разделить статусы модели и пользовательские подписи: сейчас из Engine могут показываться английские status-коды.
4. `desktop.py`: мигрировать устаревший `keybd_event` на аккуратный SendInput, обработать удерживаемые модификаторы, конфликт комбинаций, UIPI и изменение фокуса. Не вставлять в чужое окно и не нажимать Enter.
5. `server.py`: сервер по умолчанию разрешает только `base`; согласовать UI model selection с возможностями сервера. Публичный доступ сейчас не предусмотрен. Клиентское распознавание через один сервер для нескольких эфиров потребует планировщика/повторов на 503.
6. Упаковка: отделить desktop dependencies от server dependencies, зафиксировать версии, определить доставку FFmpeg/CUDA и Qt plugins. У текущего Docker CPU-образа есть лишние desktop-зависимости.

Не пытаться «закрыть» эти пункты утверждениями в документации. Проверять код и соответствующий сценарий. Набросок допустимо переработать, если сохранены требования и нет потери пользовательских файлов.

## MVP: готовые сценарии

1. Диктовка: запуск записью или Ctrl+Alt+Space, завершение, текст в истории/буфере и безопасная попытка вставки.
2. Живые субтитры: источник аудио, сегменты, компактный остров и отмена.
3. Медиа: импорт, распознавание, плеер, переход по таймкодам, правка и экспорт.
4. Эфиры: прямые HTTP(S)-ссылки, ключевые слова, совпадения с источником и временем.
5. История: локальное хранение, поиск и повторное открытие сессии.

## Ближайшая итерация после MVP

Пройти ручный чеклист на целевой Windows: микрофон, системный звук, Ctrl+Alt+Space, вставка в Блокнот и браузерный чат без Enter, импорт MP3/MP4, второй экран, один прямой эфир, отключение сети и закрытие во время inference. Затем заняться установщиком и стабилизацией live-расшифровки.

Согласовать значение «все устройства» перед упаковкой/платформенной переработкой. Для текущего Windows-ядра, тестов, UI и диктовки это не блокер. Не начинать писать статью вместо программы.

## Итерация live и караоке, 2026-09-07

- Live-субтитры стали приоритетным сценарием интерфейса. Мониторинг эфиров не показывается в навигации и не развивается в этой ветке.
- `engine.py` отдаёт `words` с границами слов. `storage.py` сохраняет их как `words_json`, при открытии старых сессий поле остаётся необязательным.
- `karaoke.py` формирует ASS с `\k`-таймингами и запускает безопасный list-аргумент FFmpeg без shell. MP4 для аудио требует выбранную обложку; MP4 для видео сохраняет исходное изображение.
- Mini-island использует исходный RMS-уровень из capture. Декоративная форма столбцов не меняет значение уровня и служит только для читаемости анимации.
- Поддержаны русская речь по умолчанию и режим `translate`, который соответствует ограничению Whisper Translate: целевой язык - английский.

После этой итерации нужны ручные проверки: drag на нескольких DPI, click-through с возвратом по горячей клавише, микрофон/наушники, FFmpeg export на аудио с обложкой и на видео.

## Итерация визуала острова и Live, 2026-09-07

Остров больше не фиксированный прямоугольник 604×132. Он меняет размер по фазе (готов, слушает, субтитр, распознаю, ошибка) и держит якорь сверху по центру. Live в полном окне - сцена текущей фразы, а не карточка статуса. Для зала есть отдельное окно субтитров (`caption_overlay`), клики через него проходят. RMS waveform по-прежнему из capture. Offscreen-проверка грузит Segoe UI из `C:\Windows\Fonts`, потому что плагин `offscreen` иначе рисует пустые глифы.

## Итерация Live loopback, 2026-09-07

Live больше не берёт общий `source=microphone`. Диктовка остаётся на микрофоне, Live по умолчанию открывает WASAPI loopback (`live_source=system`), даже если в старых настройках выбран микрофон. На этой машине звук шёл в G435, а Live слушал USB-микрофон UNA и поэтому не видел компьютерное аудио.

На острове Live источник переключается кнопкой: микрофон, звук системы, Авто. Авто (`mixed`) складывает оба потока; если одна сторона не открылась, остаётся вторая. Диктовка этой кнопки не видит.

Live-субтитры на экране берут черновик с окна ~1 с каждые ~0,35 с (greedy, без VAD и таймкодов) и финалят фразу примерно через 1,5 с или 0,24 с тишины. «Секунда в секунду» на CPU реально на профиле Быстро (`tiny`); `large-v3` этот ритм не держит. Оверлей сразу показывает прошлую фразу и текущий черновик.

## Итерация низкой задержки Live, 2026-09-07

- `pipeline.py` различает preview и final. Preview строится на активной фразе
  после 0,8 секунды речи и затем обновляется через 0,8 секунды. Он хранится
  только в памяти и никогда не записывается в SQLite.
- Очередь preview содержит только свежий снимок. Final после паузы, лимита
  фразы или Stop имеет приоритет, а переполнение ограниченной очереди сообщает
  о перегрузке вместо скрытого роста задержки.
- `engine.py` использует greedy decode для `live_preview`; финальные сегменты
  остаются в выбранном профиле. Перед стартом capture Live асинхронно готовит
  модель.
- `CaptionOverlay` автоматически открывается на время Live, не оставляет
  пустое окно в других режимах и показывает статус подготовки или перегрузки.
  Остров и Live-сцена показывают тот же предварительный текст. В QML разделены
  уведомления аудиометра, субтитра и списка финальных сегментов.
- Автоматические проверки: 76 passed, Ruff без ошибок, QML offscreen smoke-test
  прошёл через `PYTHONPATH=src`. Остаются два известных предупреждения из
  FastAPI/Starlette TestClient.

Дальше нужна ручная проверка на целевом Windows: измерить cold/warm время до
первого субтитра, RTF и P50/P95 задержку для микрофона и WASAPI loopback. Не
заявлять интервал 0,8 секунды как фактическую скорость, пока эти замеры не
сохранены для конкретного CPU/GPU и модели.

## Итерация Live catch-up и принудительная остановка, 2026-09-07

- Live больше не убивает сессию, когда модель отстаёт. Неначатая фраза
  вытесняется более новой; статус «Догоняем звук», а не фатальная ошибка.
- Финалы и preview Live идут greedy без второго Silero VAD. Preview берёт
  окно до 1,8 с. Диктовка сохраняет профиль качества и строгую очередь.
- На острове во время «Завершаем» есть кнопка принудительной остановки.
  `cancel` через 1,5 с отпускает UI, даже если CTranslate2 ещё не вернулся.

Автоматические проверки: 80 passed, Ruff без ошибок, QML offscreen smoke-test
прошёл. Ручная проверка: длинная речь на CPU `base`/`tiny`, Stop не должен
зависать, крестик на острове обязан снимать спиннер, субтитры должны
продолжаться при отставании модели, а не показывать фатальную ошибку
«Модель не успевает за эфиром».

## Итерация скорости и качества Live на CPU, 2026-09-08

Цель этой итерации задал пользователь: Live должен работать на процессоре
и на слабых машинах, видеокарта не подразумевается. На этой машине GPU есть,
но CTranslate2 не находит `cublas64_12.dll` и молча уходит на CPU, поэтому
все цифры ниже сняты на CPU (16 потоков, `int8`).

### Что оказалось причиной

Whisper дополняет любой вход до 30 секунд, поэтому окно в 1 секунду стоило
столько же, сколько целая фраза: `tiny` 304 мс, `base` 550 мс, `small`
1749 мс на окно любой длины. Прежний Live брал окно ~1 с каждые ~0,35 с,
то есть заведомо больше, чем машина успевала считать, и при этом отдавал
модели слишком мало контекста для русского слова.

### Что изменено

- `engine.py` декодирует live-окно напрямую через CTranslate2: длина входа
  энкодера равна длине фразы плюс 2 секунды тишины, а не 30 секундам.
  Тишина добавляется к звуку, а не нулями к мел-спектрограмме: измеренный
  пол мела для цифровой тишины равен −1,5, и нули на его месте читаются
  моделью как звук, из-за чего она пересказывала только что выданную фразу.
- Число токенов ограничено длиной окна; повтор-пересказ, который переживает
  `no_repeat_ngram_size`, отсекается по основам слов (`_drop_restart`).
- `pipeline.py` определяет речь потоковым Silero VAD (модель идёт в составе
  faster-whisper, сеть не нужна) вместо порога громкости. Измерено: речь
  через loopback распознаётся при RMS 0,0006, а белый шум с RMS 0,02
  отвергается — один порог громкости эти случаи не разделяет.
- Фраза длиной до 7 с при достижении лимита режется по последней паузе,
  а не посередине слова.
- Ритм черновиков следует измеренной скорости машины: где окно считается
  дольше интервала, черновики просят реже, а не копят очередь.
- `MODEL_BY_PROFILE`: `fast` → `base`, `balanced` → `small`, модель по
  умолчанию `small`. На `tiny` «русской речи» превращается в «меру с
  каиричев»; после ускорения `small` укладывается в бюджет Live.

### Измерено на этой машине (CPU, int8, окно 4 с)

| Модель | Прежний путь | Live-окно | Русский текст |
|---|---|---|---|
| tiny | 321 мс | 75 мс | фонетические догадки |
| base | 623 мс | 127 мс | в основном верный |
| small | 1828 мс | 355 мс | верный |

Прогон 18,8-секундной записи через настоящий конвейер в реальном времени
на `small`: 25 черновиков и 5 финальных фраз, задержка черновика 125–578 мс,
финал приходит через 0,3–0,5 с после конца фразы. На `medium` (имитация
слабой машины) черновиков стало 12 вместо 25, задержка 0,5–1,6 с, субтитры
продолжают идти. Silero VAD стоит 0,09 мс на кадр 32 мс.

Автоматические проверки: 113 passed, Ruff без ошибок, QML offscreen
smoke-test прошёл.

### Чего эти цифры не доказывают

Замеры сняты на синтезированной русской речи (SAPI, голос Irina) на одной
машине с 16 потоками. Это не WER и не замер на живом микрофоне. Не заявлять
работу на слабом железе, пока прогон не повторён на целевом устройстве:
нужны cold/warm время до первой фразы, P50/P95 задержки для микрофона и
WASAPI loopback и поведение при 2–4 потоках CPU. Отдельно проверить, что
`small` скачивается на чистой машине: модель по умолчанию стала тяжелее.

## Итерация визуального языка и движения, 2026-09-08

Пользователь потребовал переработать взаимодействие целиком: Live, появление
текста, перестановку строк и анимации. Прежний интерфейс терял текст на
каждом черновике и держал разные скругления, цвета и длительности в каждом
файле QML.

### Единые токены

`qml/Theme.js` стал единственным источником поверхностей, чернил, границ,
кеглей, скруглений, длительностей и кривых. Кривые: `easeOut` для появления
текста, `easeSpring` для нажатий и морфа острова, `easeInOut` и `easeExit`
для остального. `levelShape` задаёт одну шкалу уровня для острова,
осциллограммы и проверки устройства: усиление и корень растягивают тихую
речь до читаемой высоты, но не подменяют измеренный RMS.

### Живой текст

- `CaptionText.qml` собирает фразу из слов. Совпадающий префикс
  переиспользуется и не проигрывает появление заново, поэтому черновик больше
  не мигает целиком. Новые слова всплывают со сдвигом и масштабом, задержка
  между словами ограничена сверху.

## Итерация читаемых субтитров и чувствительности, 2026-09-08

Продолжение той же сессии. Пользователь добавил: субтитры должны исчезать,

### Стабильная раскладка живой строки

Причина «плывущего» текста: строка пересобиралась и переносилась заново на
каждом черновике, а центрирование заставляло её ещё и ехать по горизонтали.
`CaptionText` переработан:

- подтверждённые слова застывают на своих позициях (frozenCount); живой
  хвост продолжает строку от последнего застывшего слова и переносится,
  только когда строка заполнена; пересчёт идёт от точки продолжения, а не
  по всей фразе;
- сцена и зал выровнены влево: центр больше не двигает читаемую строку;
- раскладка вызывается сразу после синхронизации модели, а не через
  callLater, - слова больше не могут остаться в (0,0) стопкой («одно
  слово, остальные нет» - это они лежали друг на друге нерасставленные);
- сдвиг ленты вверх анимируется один раз на новую строку, а не на каждый
  черновик.

Подтверждение фразы при финале идёт волной по словам (Timer, шаг 16-48 мс,
волна короче 360 мс): видно, какие слова дозрели, а не мгновенная смена
прозрачности всей строки. Волна до трёх слов подтверждается сразу.

### Звук без речи и тишина

- Громкий звук без единой распознанной фразы дольше 8 с показывает статус

  шум?») - вместо молчаливой заморозки последней фразы.
- Тишина дольше 3 с очищает субтитр: законченная реплика не висит на
  экране до конца сессии. Оба порога - константы контроллера

## Итерация сплошных субтитров и приоритетов скорости, 2026-09-08

Пользователь попросил переработать live-режим: убрать пословную подсветку,
дать нормальную компоновку и ускорить вывод. Выбор сделан уточняющими
вопросами: текст целыми строками, первая фраза и финализация - приоритет,
машина - CPU без GPU.

### Отображение одного сплошного текста

`CaptionText.qml` переписан с пословного рендера на один сплошной текст.
Слова больше не всплывают по одному, черновик не приглушается, подтверждение
не идёт волной. Подтверждённая и предварительная части склеиваются в одну
строку (`confirmed` + `pending`) и рендерятся единым `Text`. `animateWords`,
`pendingOpacity`, `frozenCount` и волновые токены стали лишними; поле
`animateWords` сохранено ради мест, которые передают reduce_motion, и на
отображение не влияет.

Блок прижат книзу и обрезается сверху: сцена и окно зала фиксируют высоту
заранее (maxLines строк), поэтому текст не двигает окно на каждом черновике,
а длинная фраза видна последними строками. Склейка происходит в одном
read-only свойстве, поэтому в кадр не попадает промежуточный снимок
старый pending + новый confirmed.

`tests/test_caption_qml.py` переписан под новый контракт: есть отдельный
`captionBlock` (Text) вместо словесных делегатов; проверены склейка без
задвоения пробела, фиксированная высота под строки, обрезка до последних
строк и отсутствие мигания при переписывании черновика.

один финал в самом конце. Изменены константы `pipeline.py`:

- `LIVE_PREVIEW_MIN_SECONDS` 1.2 → 0.9 и `LIVE_PREVIEW_INTERVAL_SECONDS` 0.5

  ранний черновик над шумом не «просочился»: на записи тишины и треков отсев

- `LIVE_PHRASE_SECONDS` 7.0 → 6.0: длинный монолог без пауз бьётся раньше,

- `LIVE_SILENCE_SECONDS` 0.5 → 0.42: конец реплики с короткой паузой

- Оставлена `preview`/`final` склейка соседних фраз (`FINAL_MERGE_*`):

### Измерено на этой машине (16 потоков, 16 ГБ ОЗУ, RTX 3060 Laptop 6 ГБ)

- Готовые колёса `llama-cpp-python` под Python 3.12/Windows есть для CPU и для
  CUDA (cu121-cu124); Vulkan и ROCm под 3.12 не собраны, и каталог это
  показывает, а не обещает.
- CPU-сборка: Qwen3 4B Q4_K_M загружается в память за 2,8-9,8 с и выдаёт
  2,0-6,4 токена в секунду (машина в это время была занята другими задачами,
  поэтому разброс большой). Изложение записи на две минуты - 38-92 с, ответ на
  вопрос - 2-53 с.
- Режим размышления Qwen3 стоит вдвое дороже при том же ответе: 73,9 с против
  30,2 с на одном и том же запросе. Поэтому в запрос добавляется `/no_think`, а
  служебный блок `<think>` вырезается из потока.
- Запись 75 минут, 374 фразы, 29 частей: вопрос с редким словом («что решили по
  смете») отвечается за **182,6 с**, открыты 2 части из 29, карта не строится.
  Сама карта на этой машине стоит 40-60 с за часть, то есть 20-30 минут на всю
  запись; она нужна для изложения и для вопросов без общих слов с записью.
  Отсюда следующий шаг: собирать карту в фоне после окончания записи, а не в
  момент первого вопроса.
- CUDA-сборка из публичного индекса (cu124) **не запустилась на этом
  процессоре**: библиотека импортируется, а `llama_init_from_model` падает с
  0xC000001D (недопустимая инструкция) даже при нулевой выгрузке слоёв. Ошибка
  переведена в понятное сообщение с предложением вернуться к сборке
  «Процессор». До этого падения было видно, что путь верный: после установки
  `nvidia-cublas-cu12` и `nvidia-cuda-runtime-cu12` llama.cpp нашла карту
  (6143 МиБ, compute 8.6) и планировала все 44 слоя на видеокарту.
- Побочный результат тех же двух пакетов: CTranslate2 на этой машине **начал
  видеть CUDA** (`cuda_devices = 1` вместо нуля), то есть у Whisper появился
  шанс на GPU. Реальная скорость Whisper на GPU здесь не замерена.

### Чего эти цифры не доказывают

Скорость снята на одной машине, на синтезированной расшифровке совещания и при
занятом процессоре - это не бенчмарк. Качество ответов проверено на этом же
тексте: 4B-модель верно собирает изложение и отвечает с таймкодами, но
ошибается в частностях (один раз «50 тыс.» вместо «150 тыс.»). Ни один ответ
модели нельзя показывать как расшифровку: это отдельный текст рядом с ней.
GPU-путь llama.cpp на этой машине не работает, значит утверждать ускорение на
видеокарте нельзя до проверки на другом железе или на другой сборке.

## Итерация аварийного выхода и раскрытой истории, 2026-09-08

Пользователь попросил: Ctrl+C в консоли должен закрывать программу, плюс

старый текст крупнее и заметнее; клик по тексту/скролл раскрывает историю фраз
с прокруткой вверх-вниз.

### Аварийный выход (полный, сразу)

- Консоль запуска `python -m dotaudio` / `dotaudio.exe`: обработчики `SIGINT`
  (Ctrl+C) и `SIGBREAK` (Ctrl+Break) переводят контроллер в полное завершение,
  а если за 2,5 с нативный декодер не вернул управление - процесс жёстко
  завершается `os._exit`. Workers - daemon-потоки, поэтому незавершённая
  операция умирает вместе с процессом, а не роняет стек.
- Сердцебиение Qt (`QTimer` 250 мс) будит event loop: обработчик Python-сигнала
  выполняется на ближайшей границе байткода, а не откладывается, пока Qt-цикл
  ждёт событие в C++.
- Глобальная `Ctrl+Alt+X` (не переназначается страницей горячих клавиш, merge в
  `Desktop.set_hotkeys`) эмитит `quit_requested` → тот же `abortEmergency`.
  Повторное нажатие/сигнал во время выхода завершает жёстко.
- `Controller.abortEmergency()`: снимает `_closing`, останавливает активные
  сессии как forceStop (без ожидания долгого завершения), возвращает UI в idle,
  снимает крутилку подготовки модели.
- Правки: `app.py`, `desktop.py` (действие quit + merging), `controller.py`
  (slot abortEmergency), тесты TLC в test_controller.py. Все 158+ тестов зелёные.

### Отображение предыдущей строки

резервирует заметный блок контекста — предыдущая фраза крупнее прежней
подписи и не приглушается так сильно (`historyAlpha` 0.4 → 0.62). Хвост черновика

### История фраз в окнах

стоит MouseArea: клик по тексту и прокрутка колёсиком раскрывают панель истории

(`locked`, клики проходят сквозь), поэтому интерактивной истории там нет;

## Итерация чтения живого текста и спокойного интерфейса, 2026-09-08

Пользователь сказал прямо: почти ничего не работает нормально, интерфейс
лагает и дёргается, а живой текст «превращается в кашу», читать его и
работать с ним невозможно. Разбор вёлся шестью подагентами по областям
(конвейер, контроллер, оболочка QML, субтитры, остальные функции, документы),
после чего правки делались по найденным причинам, а не по общему ощущению.

### Живой текст: один поток вместо трёх видов одного и того же

Причина «каши» оказалась не в анимации, а в композиции. Одну и ту же речь
показывали одновременно три виджета: лента сверху (однострочные огрызки по
центру с затуханием по индексу), строка «предыдущая фраза» внутри сцены и
выпадающая панель истории. Выравнивание, кегль и обрезка у них были разные,
а высота ленты пересчитывалась от содержимого, поэтому текст ещё и ездил.

`LiveTranscript.qml` заменяет все три. Это одна колонка: сказанные фразы
читаются сверху вниз целиком (перенос по словам, ничего не обрезается
многоточием), у каждой - таймкод и кнопка копирования при наведении, текст
можно выделить мышью. Живая строка стоит последней, её место (3 строки)
отведено заранее и не зависит от длины фразы. Список прижат к живой строке
снизу, поэтому при двух фразах между ними нет пустого поля, а на длинном
разговоре список упирается в верх и прокручивается; у верхнего края - мягкое
затухание, чтобы обрезанная строка не выглядела рваной. Лента следует за
речью, пока пользователь сам не отмотал вверх - тогда появляется «К текущей
речи». Панель истории и настройки `live_click_history` / `live_show_previous`
удалены: список и есть история. Вместо них - `live_show_times`.

Полоса управления Live была из двенадцати элементов подряд; осталось то, что
трогают во время речи (источник, чувствительность, зал), остальное - под
кнопкой «ещё». Тесты `test_caption_qml.py` дополнены тремя проверками:
живая строка не двигается при росте истории и текста, список никогда не
залезает на неё, текст фраз не обрезан.

### Почему интерфейс дёргался

- `changed` был шиной всего интерфейса: по нему перечитывались настройки,
  журнал, устройства и карточки моделей. Его слал секундный таймер во время
  любой записи и каждая распознанная фраза. Теперь у строки состояния,
  счётчика времени, журнала и субтитра отдельные сигналы, а `changed`
  остаётся их надмножеством (связи в `__init__`), поэтому остальной код не
  менялся. `_tick` шлёт только `elapsedChanged`.
- `Waveform` десять раз в секунду пересоздавал массив и запускал до 48
  одновременных анимаций высоты, в трёх экземплярах сразу. Переписан на один
  холст с кольцевым буфером; скрытая полоса не считает вовсе.
- Окно субтитров зала пересчитывало своё положение на каждый `changed`, то
  есть каждую секунду записи. Теперь - только при смене настроек размещения.
- Морф острова меняет размер настоящего окна. Пружина по ширине заставляла
  окно проехать мимо цели и вернуться; убрана, длительность 380 → 260 мс.
- Наведение больше не раздувает кнопки (1.02-1.06): панель из десятка кнопок
  не должна пульсировать под курсором. Нажатие по-прежнему проседает.
- Караоке-просмотр перебирал весь список фраз на каждый кадр воспроизведения;
  теперь список перебирается только при выходе за границы текущей фразы, а
  скрытая страница не считает ничего.

### Скорость Live

`bench_tail.py` на настоящей записи (small, CPU int8): на первом окне фразы
(около секунды звука) двухсекундный хвост тишины стоил 374 мс и заставлял
декодер зациклиться («Я мёд! Ты тесно! Я мёт!»), а 1,5 с дали одну чистую
строку за 179 мс. На длинных окнах разница в пределах шума, 0,6 с начинает
срезать конец фразы. `LIVE_TAIL_SECONDS` 2.0 → 1.5. Сквозной прогон
`sim_live.py` на записи 7,7 с: первый черновик 1,17 с вместо 1,38 с, текст
совпадает с прежним.

### Черновик перестал дорожать вместе с фразой

Черновик распознаёт всю активную фразу целиком, поэтому его цена росла вместе
с ней: на записи речи 18,8 с задержка шла 141 → 1079 мс, и текст к концу
длинной реплики появлялся рывками.

Сначала пробовали окно короче фразы (3,5 с) с переносом вышедшей из окна речи
в подтверждённую часть. Задержку это выровняло, но на настоящей записи
вскрылась цена: на окне, которое начинается посреди фразы, декодер иногда
переставляет слова («Почти мгновенно, даже в титры должны появляться»), и
границу сказанного тогда не найти ни точным совпадением, ни выравниванием
последовательностей - на экран попадал обрывок вместо реплики. Читать обрывки
хуже, чем ждать лишние сто миллисекунд.

Поэтому окно снова равно фразе, а ограничена сама фраза:
`LIVE_PHRASE_SECONDS` 6.0 → 4.0. Замер на той же записи: задержка черновика
141-500 мс без роста, каждый черновик показывает фразу целиком, финалов 6
вместо 5, итоговый текст совпадает. Медиа-тесты на настоящей речи
(`records_the_whole_sentence`, `keeps_emitting_after_repeated_real_speech`)
прошли, то есть целые реплики не потерялись.

Механизм переноса (`_phrase_head`, `_shift_cut` на `SequenceMatcher`) оставлен:
на медленной машине окно всё ещё может отстать от фразы, и тогда сказанное
переносится, а окно с неизвестной границей просто не показывается - прежний
субтитр висит до следующего, а финал приходит полным.

### Оболочка разобрана на страницы

`MainMvp.qml` был на 2247 строк со всеми семью разделами внутри, и все они
жили в памяти сразу - включая плеер и вторую Live-сцену. Страницы вынесены в
`DictationPage.qml`, `MediaPage.qml`, `ModelsPage.qml`, `HistoryPage.qml`,
`SettingsPage.qml`; в оболочке осталось 945 строк. Каждая страница создаётся
`Loader`ом при первом открытии (`asynchronous`) и дальше живёт, чтобы не
терять состояние плеера и прокрутку. Перенос делался скриптом

## Итерация голосов NVIDIA NeMo в расшифровке файла, 2026-09-08

Пользователь попросил добавить модель NeMo для распознавания разных голосов
в расшифровке аудио из файла и удобный интерфейс к ней.

### Почему не `nemo_toolkit`

Python-пакет NeMo на Windows не работает: в матрице поддержки NeMo Framework
для `windows-amd64` стоит «No support yet» и по обоим способам установки,
а официальная инструкция предлагает WSL. Ставить рядом torch и WSL ради
одной функции настольного приложения неразумно.

Взят **NeMo-Speech.cpp** - собственный нативный рантайм NVIDIA для тех же
моделей (ggml, Apache-2.0). Он ставится одним архивом в
`%LOCALAPPDATA%\Programs\NeMoSpeech`, не тянет torch и Python вообще, умеет
CPU/CUDA/Vulkan и содержит команду `diarize` с моделью
`nvidia/diar_streaming_sortformer_4spk-v2` (140 МБ, CC-BY-4.0). Проверено на
этой машине: `doctor` отвечает `"diarization": true` на профиле CPU.

### Что добавлено

- `nemo_diarize.py` - Qt-free обёртка над CLI. Поиск исполняемого файла в
  PATH и в каталоге установщика (уже запущенный процесс не видит PATH,
  дописанный установщиком), `probe()` для карточки готовности,
  `ensure_model()` отдельным шагом до прохода, разбор `--format json`.
  Запуск - списком аргументов без shell, окно консоли не всплывает.
  Отмена здесь настоящая: процесс убивается, в отличие от кооперативной
  остановки нативного декодера Whisper.
- `speaker_id.py` - общий контракт для обоих движков. `assign_turns()`
  раскладывает фразы по размеченной дорожке: голос выбирается по
  наибольшему пересечению, слово из паузы забирает ближайший отрезок в
  пределах 0,75 с, а фраза со сменой голоса **разрезается по границе** -
  этого прежний путь по одному эмбеддингу на фразу не умел в принципе.
  Перескок короче 0,35 с между одинаковыми соседями считается дрожанием
  границы и поглощается; реплика в стык двух разных голосов остаётся.
  Текст фразы пересобирается только у настоящего разреза, иначе исходная
  строка распознавания сохраняется дословно.
- `controller.py` - настройка `diarize_engine` (`nemo` / `ecapa` / `off`),
  фоновый опрос рантайма, легенда с числом реплик и временем речи каждого
  голоса, этапы прохода (слова / голоса). Неудача диаризации больше не
  отменяет расшифровку: текст остаётся, причина уходит в подпись.
- `TranscriptView.qml` - выбор движка с индикатором готовности, карточка
  установки с командой и кнопкой «Копировать», полоса голосов по всей
  записи с переходом к фразе по клику, фильтр «только этот голос»,
  цветовые роли говорящих. В `Theme.js` добавлены `speakerInks` -
  единственное отступление от монохрома: четыре приглушённых тона, потому
  что одной яркостью серого четыре голоса не развести.

### Измерено на этой машине (CPU, i5-12500H)

Двухголосая запись 19,1 с собрана из двух разных источников
(`.local-bench/mix_speakers.py`), эталонная раскладка известна по построению.

| Что | Результат |
|---|---|
| Отрезки NeMo против эталона | 8 из 8 верно, ровно 2 голоса |
| Диаризация | 4,2 с на 19,1 с звука, RTF 0,22 |
| Whisper `small` на той же записи | 9,1 с |
| Разметка фраз (`bench_voices.py`) | 9 строк, все 9 с верным говорящим, 1 фраза разрезана по смене голоса |

Автоматические проверки: `pytest -q` 219 passed, 11 skipped; QML offscreen
smoke-test exit 0. Новых тестов 33: разбор ответа CLI, поиск рантайма,
`probe` на всех состояниях, отмена живого процесса, разрезание фразы,
дрожание границы против настоящей реплики, нумерация ролей, легенда и
поведение при отсутствующем рантайме.

### Чего эти цифры не доказывают

Это **не DER**. Запись двухголосая и склеена из двух источников, то есть
голоса заведомо далеки друг от друга; настоящие тяжёлые случаи -
перебивания с наложением речи, три-четыре похожих голоса, один микрофон на
комнату - не проверялись вовсе. Sortformer различает не больше четырёх
голосов, пятый он куда-нибудь припишет. Скачивание модели
проверено один раз на быстрой сети; поведение `pull` при обрыве связи
руками не воспроизводилось. Интерфейс снят offscreen: полоса голосов,
фильтр и переход к фразе по клику на живом экране не нажимались.

### Видеокарта, замерено там же

Для Windows опубликован готовый архив `windows-x86_64-cuda` (101 МБ), поэтому
сборка из исходников не нужна: CUDA Toolkit не требуется, хватает драйвера.
После переустановки рантайма профилем `cuda` на RTX 3060 Laptop (драйвер
591.59) `doctor` показывает `accelerator_available: true` и устройство CUDA0.

| Запись | CPU, три прогона | CUDA, три прогона |
|---|---|---|
| Речь 19,1 с | 4,24 / 4,29 / 5,01 с | 0,72 / 0,71 / 0,70 с |
| Трек 60 с | 20,15 / 20,84 / 20,69 с | 2,05 / 2,05 / 2,02 с |

То есть RTF падает с 0,22-0,34 до 0,034-0,037: на минуте звука это 20 с
против 2 с. В полном проходе диаризация перестала быть заметной статьёй -
на записи 19,1 с она занимает 0,9 с против 11,2 с у Whisper `small`.

Выбор устройства берётся из общей настройки `device`: "auto" оставляет выбор
рантайму, явные "cpu"/"cuda" уходят в `--device`, чтобы диаризация не заняла
видеокарту, когда пользователь увёл всё на процессор.

На чистой речи разметка CPU и CUDA совпала дословно, все восемь отрезков.
На музыкальном треке бэкенды разошлись: один отрезок из восьми получил
разного говорящего и границы поехали на 80 мс. Это ожидаемая разница
вычислений с плавающей точкой на трудном материале, где модель и так не
уверена, но означает, что разметку песни нельзя считать воспроизводимой
между устройствами.

## Итерация отклика ассистента, 2026-09-08

Пользователь: интерфейс троттлит и подмерзает при открытии ассистента и
выборе локальной модели.

### Причины

- `selectModel` / `unload` / `shutdown` вызывали `engine.release()` на
  GUI-потоке: `close()` у GGUF идёт секундами и останавливает event loop.
- Сохранение `assistant_model` шло через `Controller.setSetting` → общий
  `changed`, и весь мост (остров, настройки, устройства) перечитывался.
- Прогресс загрузки и каждый токен ответа слали широкий `changed` /
  `messagesChanged`: лист каталога и пузыри чата пересобирались десятки
  раз в секунду.
- `_guard` на GUI повторно трогал Ollama/llama; страница ассистента и
  каталог моделей жили в дереве всегда, даже закрытыми.

### Что изменено

- Выгрузка модели - в daemon-потоке; `shutdown` больше не ждёт close().
- Настройки ассистента пишутся без общего `changed` у моста записи.
- Узкие сигналы: `modelChanged`, `hardwareChanged`, `downloadChanged`,
  `noticeChanged`, `recordChanged`; прогресс загрузки ~8 Гц, токены ~20 Гц
  через `pendingReply` без пересборки списка.
- Выбор записи и опрос каталога - в фоне; страница и каталог - через
  `Loader` при первом открытии.

Проверки: `pytest -q` 317 passed, 11 skipped; Ruff чист; QML smoke-test
exit 0 за ~12 с (раньше выход мог тянуться около минуты из-за release).

## Итерация предложений вместо обрывков в Live, 2026-09-08

Пользователь: Live показывает слова обрывками, читать тяжело; приоритет -
скорость распознавания и текст слово в слово.

### Что оказалось причиной

Скорость сама по себе была в норме (черновик 140-500 мс на `small`, CPU
int8), обрывки давал способ показа. Фраза режется по лимиту 4 с, и каждый
кусок приходил отдельным финалом и отдельной строкой истории: «Сегодня мы
говорим о распознавании русской речи в реальном» / «времени.» Декодер видел
каждый кусок сам по себе: не знал, что было сказано до него, ставил точку в
конце любого окна и заглавную букву в начале следующего. На записи 18,8 с
это давало шесть строк на четыре предложения.

### Что изменено

- `engine.py`: live-окно получает предыдущий распознанный текст как
  `previous` токены промпта (`RecognitionConfig.live_context`, до 200
  символов, режется по слову). Эхо контекста в ответе снимается `_drop_echo`
  по основам слов, чтобы повтор промпта не попал на экран.
- `pipeline.py`: `LiveSession` держит три последних финала (`_context`) и
  передаёт их в черновик и финал; для короткого финала с lead-звуком
  контекст без последней фразы, иначе она читалась бы дважды. Финал несёт
  флаг `cut` - фраза оборвана лимитом, а не паузой; `SpeechBuffer`
  различает `flush_at_limit` и `flush`, слияние финалов в очереди флаг
  сохраняет.
- `transcripts.py`: `sentence_open`, `continues_sentence`, `blend_fragments`,
  `join_fragments`. Финал с `cut` считается серединой предложения, что бы ни
  поставил декодер; без `cut` предложение открыто, пока нет `.!?…`.
  Продолжение принимается при паузе до 2 с и длине до 320 символов, а также
  когда следующий кусок начинается со строчной буквы. На шве «мгновенно.» +
  «Даже» точка становится запятой, заглавная - строчной; `?` и `!`, имена и
  аббревиатуры не трогаются.
- `controller.py`: `_extends_open_phrase` дописывает продолжение в тот же
  сегмент (`Store.extend_segment`) вместо новой строки; живая строка =
  открытое предложение + черновик (`_refresh_live_caption`); пауза
  `LIVE_CLEAR_SILENCE_SECONDS` и остановка закрывают предложение
  (`_close_open_phrase`). Новые свойства `liveOpenPhrase` и
  `settledCaption`: остров и зал показывают последнее законченное
  предложение, пока не началась новая речь.
- QML: `LiveTranscript.hideLast` убирает открытое предложение из колонки
  истории, оно читается в живой строке; `MiniIsland` и `CaptionOverlay`
  падают на `settledCaption`, когда живой строки нет.

### Измерено (small, CPU int8, живой конвейер, `sim_live.py`)

Запись 18,8 с: 25 черновиков, задержка 94-422 мс (без роста), финалов на
уровне конвейера по-прежнему 6, строк на экране и в истории - 3:

- «Привет.»
- «Сегодня мы говорим о распознавании русской речи в реальном времени.»
- «Живые субтитры должны появляться почти мгновенно, даже на слабом
  процессоре без видеокарты. Это главная задача текущей эти рации.»

WER 10,7 % против эталона (единственная ошибка «эти рации» была и раньше).
Запись 7,7 с (`speech_video`): один абзац из трёх кусков, WER 16-20 % с
контекстом и без - в пределах шума одной записи. Медиа-тесты
`test_live_media.py` на записи и пяти треках прошли: музыка не стала
субтитрами, контекст не добавил выдумок сквозь порог `-1.0`.

Второй прогон той же записи шёл под чужой нагрузкой (параллельный бенчмарк
LLM забирал ~10 ядер, задержка черновика выросла до 4 с): все слова всё
равно дошли до трёх строк с тем же WER, потерь текста при отставании нет.

### Проверки

`pytest -q`: 313 passed, 11 skipped (+ 4 в `test_assistant_qml.py`
offscreen); `ruff check src tests` чист. Новые тесты: `test_transcripts.py`
(правила шва), `test_pipeline.py` (флаг `cut`, контекст, lead без повтора),
`test_engine.py` (промпт из контекста, граница 200 символов, эхо),
`test_controller.py` (склейка в одну строку, шов, закрытие паузой).

### Чего это не доказывает

### Что реализовано (15 пунктов)

1. **Чат по записи и общий чат** - `chat_messages`, вкладки «Записи» / «Чаты»,
   история на сессию, прикрепление `.txt` к вопросу (`AssistantPage.qml`).
2. **Карта записи (digests)** - части ~2,5 мин по границам фраз, выжимка
   каждой части один раз, свёртка длинной карты (`assistant.py`).
3. **Поиск релевантных частей** - `selective_hits` по редким словам,
   `score_chunks` (лексика + hash-эмбеддинги), до двух раундов с соседними
   частями.
4. **Готовые действия** - изложение, главные мысли, задачи/договорённости,

5. **Экспорт** - переписка и карта записи в Markdown/текст (`exportChat`,
   `exportDigests`).
6. **Кликабельные таймкоды** - `[MM:SS]` / `[H:MM:SS]` в ответе,
   `linkifyTimestamps` в QML, переход через `openTimestamp` /
   `openSessionAt`.
7. **Ответы с учётом говорящих** - метки «Голос N» в частях и промптах;
   смена роли инвалидирует `content_hash` (`speaker_labels.py`).
8. **Фоновая карта после транскрибации** - по успешному `jobFinished`
   ставится задача `index`; выжимки и embeddings считаются в daemon-потоке.
9. **StoreDigests** - кеш выжимок в памяти, load/save/clear, фильтр по
   `model_id`, инвалидация по хешу текста части.
10. **Без I/O в Q_PROPERTY** - `modelReady`, каталог и probe Ollama в
    воркере; узкие сигналы; поток токенов через `pendingReply`, не через
    `messagesChanged` на каждый токен.
11. **Очередь задач LLM** - приоритет ответа/действия над названием и
    фоновой индексацией; `queueStatus`; срочная задача отменяет `index`.
12. **Hash-эмбеддинги** - `embed_text` (feature hashing, dim=256), таблица

13. **VRAM arbiter** - mutex «asr» / «llm», evict через callback;

14. **Subprocess llama worker** - `llm_worker.py`, JSON-lines stdin/stdout;

15. **Seek из чата** - `Controller.openSessionAt`, `pendingSeekMs`,

   ошибками загрузки нет. В рантайме `Loader` страницы моделей отдаёт item.

### На заметку

Страницы навигации создаются асинхронными `Loader`, поэтому `--smoke-test` их
не касается: он поднимает только корень `MainMvp.qml`. Ошибку в отдельной
странице ловит покомпонентная проверка или открытие раздела вручную.


## Итерация читаемого черновика и каскада моделей, 2026-09-09

Пользователь: текст в Live непонятный, «простыня» дёргается и переписывается,
нужны короткие части, лучше качество и практически синхронное появление.

### Что оказалось причиной «простыни»

1. `_refresh_live_caption` подставлял в живую строку открытое предложение из
   истории (до 140 символов) и склеивал его с черновиком. Строка росла на
   несколько реплик и переписывалась целиком 3-4 раза в секунду, а из колонки
   при этом пропадала (`hideLast: bridge.liveOpenPhrase`).
2. Подтверждённая часть публиковалась прямо от согласия двух гипотез
   (`_stable_prefix = agreed`). Соседние окна отличаются на сотню
   миллисекунд, поэтому согласие получало и неверно услышанное слово, а
   следующее окно его переписывало.

### Что изменено

- Живая строка - только текущая фраза: согласованный префикс как
  подтверждённая часть, остаток гипотезы как черновик. Готовые фразы стоят
  в колонке и больше не переписываются (`hideLast: false`,
  `closedCount = segments.length` в окне зала).
- Фраза `LIVE_PHRASE_SECONDS` 4.0 -> 2.2 с, строка истории
  `LIVE_SENTENCE_MAX_CHARS` 140 -> 90, окно показа 110 -> 90: речь уходит
  в колонку короткими единицами чтения, а не одним куском.
- `LIVE_CONFIRM_LAG_WORDS = 2`: подтверждаются согласованные слова без
  последних двух - у края окна декодер их ещё уточняет.
- `_publish_stable`: подтверждённая часть растёт и не сжимается, пока новая
  гипотеза начинается с тех же слов. Настоящее переписывание уступает
  декодеру: слова остаются на экране, но снова читаются как черновик.
- Первый черновик 0.5 -> 0.4 с, интервал 0.28 -> 0.22 с.

### Каскад двух моделей

`RecognitionConfig.live_draft_model` и отдельный `Engine` для черновиков
(`LiveSession(draft_engine=...)`, настройка `live_draft_model`: авто / base /
small / одна модель). Один движок держит в памяти одну модель, поэтому общий
движок вытеснял бы её между черновиком и финалом несколько раз в секунду.
Если быстрая модель не поднялась, черновики считает выбранная: Live не теряет
субтитры из-за необязательного ускорения.

`vram_arbiter.on_evict` держит список callback-ов на владельца: с одной
ссылкой вторая модель Whisper оставалась в видеопамяти после вытеснения.

### Измерено (RTX 3060 Laptop, CUDA, speech_video.wav 7,71 с, эталон refs.json)

| Финал | Черновик | 1-й черновик | Цена черновика | Отстаёт p50/p95 | Строк | WER |
|---|---|---|---|---|---|---|
| small | тот же | 953 мс | 94 мс | 0 / 50 мс | 3 | 34,8% |
| medium | тот же | 1125 мс | 219 мс | 125 / 328 мс | 3 | 26,1% |
| medium | small | 938 мс | 78 мс | 0 / 7 мс | 3 | 26,1% |
| medium | base | 953 мс | 47 мс | 0 / 13 мс | 3 | 26,1% |
| turbo | small | 937 мс | 79 мс | 0 / 65 мс | 3 | 34,8% |

«Отстаёт» - разница между часами и концом окна показанного текста, то есть
насколько субтитр позади звука. Строки истории: медиана 43 символа, максимум
61 (прежде одна строка собирала до 140). Разморозок прочитанного текста
осталось 2 на 15 черновиков, и обе - настоящая правка декодера; в одном
случае заморозка удержала слова.

### Про vosk как «ведущий край»

Пользователь предлагал vosk + Whisper. По замерам проекта
(`docs/STT_METHODS.md`) у vosk WER 52% против 8-26% у Whisper, а каскад уже
даёт отставание 0-7 мс: второй движок с худшим русским вернул бы ту самую
чехарду слов. `live_engine=vosk` остаётся явным выбором для слабого CPU.

### Чего это не доказывает

Одна запись 7,71 с на одной машине с CUDA - это не корпусный WER. Каскад
измерен только на GPU: на CPU обе модели делят те же ядра, и выигрыш не
проверялся (там `adapt` планирует small/base, где каскад не включается).
Расход видеопамяти каскада (~2 ГБ на medium+small) на картах 4 ГБ и меньше не
проверялся. Читаемость оценена числами, а не глазами на живом экране. Полный
`pytest -q` в этом дереве падает на чужом незавершённом WIP (`test_engine.py`
про `confidence`, `test_vosk_engine`); к этой итерации те падения не относятся.

## Итерация упрощения транскрибации, 2026-09-09

Пользователь: страница перегружена, лишние кнопки, окна перекрывают друг
друга, скролл не доведён.

### Что убрано из интерфейса

- SplitView и отдельный скролл шапки: одна колонка, список фраз занимает
  оставшуюся высоту и крутится сам.
- Панель `TranscriptTools` (поиск/замена, пресеты, сравнение моделей).
- Карточка «сейчас звучит», полоса mute/solo, In/Out/Loop, разрезать/склеить,
  метки проверки, AI на фразе, ассистент, режим речи, подсказка поверх списка.
- Файлы инструментов не удалялись - страница их больше не показывает.

### Что осталось

Открыть / расшифровать / стоп / сохранить / очистить; модель и голоса в
одной строке; плеер (play, шкала, скорость, звук); чипы говорящих; список
фраз с кликом и правкой.

### Доделка раскладки

Циклические `anchors.fill` + `implicitHeight` у шапки и карточек ломали
высоту, из-за этого список обрезался и скролл не доезжал до конца.
Шапка и фразы считают высоту от содержимого; чипы голосов ограничены;
у списка есть подвал и вертикальный flick. In/Out/Loop из плеера убраны
совсем. Проверка: `tests/test_transcript_qml.py`.

## Итерация сохранения Live, 2026-09-09

Пользователь: Live должен куда-то складывать речь, после Stop - полная
обработка, удобный просмотр, аудио удалить.

### Что сделано

- Во время Live звук пишется потоком в `data_dir/live/{session}.wav`
  (`WavStream`), путь в `sessions.audio_path`. Черновые фразы по-прежнему
  идут в SQLite по ходу сессии.
- После Stop - один качественный проход как у файла (`media_mode`, слова,
  необязательные голоса). Черновик заменяется через `replace_segments`.
  WAV удаляется, `audio_path` очищается.
- Готовая сессия открывается в «Транскрибации»: фразы, таймкоды, экспорт,
  правка. Плеера нет - файла уже нет. Из истории тот же путь.
- Отмена Live или обработки: черновые фразы остаются, временный WAV
  удаляется. Прерванная сессия с файлом на диске при открытии из истории
  догоняет тот же проход.
- Два прохода как у диктовки не делались: Live может длиться часами.

### Проверки

`tests/test_live_process.py`, `tests/test_monitor_clips.py` (WavStream).
Сеть, микрофон и настоящая модель в этих тестах не нужны.
