# DotAudio: замысел продукта

Статус: требования и проектные предложения для следующего этапа. Описание ниже шире реализованного кода. Текущая заготовка перечислена в [HANDOFF.md](HANDOFF.md).

## Контекст и подтверждённые пожелания

DotAudio создаётся как самостоятельный проект к статье на Хабре о Whisper. Статья рассчитана на разработчиков и людей, которые собирают приложения с помощью ИИ. Автор статьи расскажет историю Whisper, пошаговый принцип работы и практические кейсы. Сейчас задача исполнителя - программа, не написание статьи.

Пользователь хочет одно приложение с переключением режимов:

- Диктовка с автоматической вставкой в активный чат или другое поле и копированием в буфер.
- Живые субтитры, в том числе для мероприятий.
- Распознавание аудио и видео, плеер, таймкоды и редактор текста.
- Мониторинг нескольких эфиров и поиск определённых новостей.
- История сессий.
- Выбор моделей Whisper и режимов вычислений.
- Компактное прозрачное окно, напоминающее Dynamic Island, вызов кнопкой и горячими клавишами.
- Высокая отзывчивость, аккуратная реализация, визуальный стиль Apple + DotCore.

Windows - явно названная первая платформа. Python предпочтителен, но пользователь разрешил выбрать технологии по результатам исследования. Фраза «на всех устройствах» осталась неоднозначной: разные Windows-ПК либо также macOS/Linux/мобильные ОС. Не выдавать текущую Windows-интеграцию за универсальную.

Timeweb - работодатель/рекламодатель пользователя. Серверные вычисления уместны, если дают практическую пользу; локальная работа допустима и обязательна как самостоятельный сценарий. Никаких серверов в этой сессии не создавали.

## Предложенная продуктовая модель

Два уровня одного приложения: компактный остров для действий во время другой работы и основное окно для файлов, истории, редактора и настроек. Переключение страницы не должно сбрасывать активную запись.

Состояния острова: скрыт → готов → слушает → распознаёт → результат/ошибка. Во время записи он показывает реальный уровень сигнала, длительность и остановку. После распознавания - краткий результат и копирование. Размер изменяется по содержимому плавно, но положение остаётся предсказуемым.

Основные страницы: «Диктовка», «Живые субтитры», «Аудио и видео», «Мониторинг», «История», «Настройки». Это навигация внутри приложения, а не шесть отдельных продуктов.

### Диктовка

1. Пользователь ставит курсор в нужное поле и нажимает горячую клавишу.
2. Приложение запоминает целевое окно и начинает захват микрофона.
3. Повторное нажатие завершает запись; Escape отменяет текущую диктовку.
4. Финальный текст сохраняется в истории и буфере обмена.
5. Автовставка выполняется только в ожидаемое целевое окно. Если фокус изменился, текст остаётся в буфере и появляется понятное сообщение.

Никогда автоматически не нажимать Enter и не отправлять сообщение. Отмена не должна вставлять частичную фразу. Не переписывать вручную набранное содержимое поля. Пользователь явно хочет оставить расшифровку в clipboard, поэтому восстановление прежнего буфера, как у некоторых аналогов, здесь не является исходным требованием.

Предложенные сочетания: Ctrl+Alt+Space для начала/остановки, Ctrl+Alt+O для острова. Нужны переназначение и обработка конфликта с другой программой. Нельзя полагаться на одну глобальную комбинацию на всех раскладках и ОС.

### Живые субтитры

Микрофон и системный звук, выбор устройства, размер текста, контраст, положение и прозрачность. Для мероприятия нужен отдельный вид субтитров на втором экране. Перевод выделяется отдельной настройкой: Whisper `translate` переводит в английский, а не в произвольный язык.

Whisper обрабатывает фрагменты аудио. Для воспринимаемого live-режима нужен слой endpointing, перекрывающихся окон и стабилизации текста. Уже подтверждённые слова не должны бесконечно переписываться или дублироваться. В исходной заготовке есть только простое разделение по энергии/тишине, без алгоритма стабилизации.

### Аудио и видео

Загрузка файла, drag-and-drop, извлечение звуковой дорожки, отображение прогресса и возможности отмены. Плеер и список сегментов синхронизированы: нажатие на реплику перемещает позицию воспроизведения; текущая реплика подсвечивается.

Редактор сохраняет исходный и исправленный текст. Далее нужны undo/redo, поиск, изменение границ сегмента с проверкой таймкодов. Экспорт TXT/SRT/VTT/JSON. Файл остаётся в исходном месте, история хранит ссылку на него; при перемещении файла нужно предложить указать новое расположение.

Обработка аудио из видео сама по себе не означает анализ изображения. OCR слайдов, понимание сцены, резюме и семантический поиск - возможные отдельные расширения, не подтверждённый состав первой версии.

### Мониторинг эфира

Первый законченный вариант: несколько прямых HTTP(S)-аудио/HLS-потоков; независимые состояния подключения, текст с таймкодами и журнал совпадений. Пользователь задаёт слова и фразы, получает контекст, источник и время события. Правила совпадения и причины срабатывания должны быть видимы.

Далее: поиск по смыслу, группировка одинаковых новостей между каналами, восстановление подключения, уведомления и сохранение коротких фрагментов вокруг события. YouTube, Telegram, обычная страница сайта и прямая ссылка на поток требуют разных адаптеров; нельзя обещать универсальную поддержку ссылок без них.

Число каналов ограничивается производительностью. Нужны очередь, мониторинг задержки и явный статус перегрузки. Незаметно терять аудио при отставании нельзя. После перезапуска найденные события должны быть доступны в истории.

## Модели и профили

| Профиль | Начальная гипотеза | Для чего |
|---|---|---|
| Быстро | tiny/base, CPU int8, короткие фрагменты | Слабые ПК, короткая диктовка |
| Баланс | base/small, auto CPU/GPU | Повседневная речь |
| Качество | large-v3 или turbo, подходящий GPU | Длинные файлы и сложные записи |
| Сервер | Тот же контракт сегментов через HTTP | Перенос тяжёлой работы на отдельный сервер |

Это кандидаты для измерений, не результаты бенчмарка. Не обещать, что одна модель будет одновременно самой точной и самой быстрой на любом устройстве. Профили не заменяют ручной выбор модели.

Нужен менеджер моделей: размер загрузки, место на диске, прогресс, отмена, готовность к офлайн-работе, предварительный прогрев. Сейчас загрузка происходит при первом распознавании. Не запускать автоматическую скачку всех моделей.

## Стиль Apple + DotCore

От Apple: ясная иерархия, крупные зоны нажатия, плавные короткие переходы, компактное окно с несколькими состояниями, минимум служебных деталей. От DotCore: монохром, тёмные поверхности, тонкая сетка, line-art и небольшая подпись `.ядро`. Не копировать логотипы и системные активы Apple.

Предлагаемые токены: фон `#0a0b0d`, поверхность `#14161a`, дополнительная поверхность `#1b1d21`, основной текст `#f3f3f1`, вторичный `#a6a7ab`, границы белым с небольшой прозрачностью. Акцент на доступность: состояние нельзя передавать только цветом.

Типографика: Segoe UI на Windows, системный шрифт на других ОС. Проверять длинные русские подписи, масштаб 125/150/200%, клавиатурную навигацию и читабельность поверх светлого видео. Скругления и glow умеренные; размытие должно иметь дешёвый непрозрачный fallback. Анимации порядка 160-240 мс - начальное предложение, не требование к замерам.

Осциллограмма отражает входной звук. Декоративные случайные столбики и фальшивые статусы «GPU активно» недопустимы.

## Как доводить до готового продукта

1. Проверить текущие контракты и исправить конкурентный доступ/остановку. Сделать полный сценарий микрофон → текст → история → буфер на реальном ПК.
2. Собрать качественный остров и диктовку: фокус, hotkeys, Escape, tray, ошибки, менеджер модели. Проверить вставку в Блокнот и браузерный чат без отправки.
3. Довести live-субтитры: стабильный текст, системный звук, второй экран, слабый CPU, отключение устройства.
4. Добавить полноценный плеер и редактор, загрузку длинных файлов, прогресс и восстановление сессий.
5. Довести мониторинг: независимые каналы, переподключение, сохранение событий, нагрузочный тест.
6. Отдельно проверить серверный путь, измерить задержку с учётом сети и только затем демонстрировать Timeweb.
7. Установщик и проверка на чистой Windows без Python. Затем решать переносимость на основе уточнённой матрицы устройств.

Все режимы остаются в целевом продукте. Этот порядок нужен для проверки законченных пользовательских сценариев, а не для исключения функций.

## Критерии качества

- UI не ждёт загрузку модели, сеть, декодирование и распознавание; интерактивные действия должны укладываться примерно в 100 мс как проектный ориентир.
- Отдельно измеряются холодный старт, тёплый запуск, время до первого текста и финализация после остановки.
- Для live оценивается RTF (время обработки / длительность аудио) вместе с растущей задержкой очереди. Значение меньше 1 необходимо, но само по себе не гарантирует приятные субтитры.
- Проверки речи: русский/английский, акценты, имена, тишина, шум, музыка, несколько говорящих. Для качества - WER/CER на фиксированной выборке, для UX - субъективная читаемость.
- Память и задержка не растут без границ после часа записи. Переключение моделей не оставляет несколько тяжёлых экземпляров.
- Неудачная вставка и ошибка модели не теряют уже сохранённый текст. Отмена не считается успешным завершением.
- Локальный режим после скачивания модели проверяется без сети. Серверный режим явно сообщает, что аудио отправляется на выбранный сервер.
- Поддержка платформ заявляется после проверки на них, не по одному факту использования Qt.

## Вопросы, оставшиеся следующему исполнителю

Не возвращаться ко всем вопросам с нуля. Пользователь разрешил принимать обычные решения самостоятельно. Уточнять перед зависимым этапом:

1. «Все устройства»: только Windows-компьютеры или также другие ОС и телефоны?
2. Мультимодальность: достаточно аудио/видео или нужен анализ изображения?
3. Какие реальные каналы нужны для демонстрации, сколько одновременно?
4. Какое оборудование и бюджет Timeweb доступны, если дойдём до сервера?
5. Как разрешить читателям статьи использовать исходники? Текущий LICENSE по стандарту DotCore не даёт разрешения на запуск/распространение.
