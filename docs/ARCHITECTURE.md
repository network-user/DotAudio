# Архитектура и принципы разработки

## Выбранная основа

Python 3.12 + PySide6/Qt Quick/QML. Python управляет приложением, а Qt отрисовывает интерфейс; распознавание выполняется faster-whisper на CTranslate2. Поэтому сам по себе Python не определяет скорость нейросети. До смены стека сначала измерять UI, захват, очередь, декодирование и inference отдельно. [Qt Quick + Python](https://doc.qt.io/qtforpython-6/quickstart.html), [faster-whisper](https://github.com/SYSTRAN/faster-whisper).

Qt позволяет переиспользовать часть приложения на настольных ОС. Горячие клавиши, вставка, системный звук, разрешения и упаковка всё равно требуют платформенных реализаций. Мобильный клиент пока не выбран.

Текущие зависимости находятся в `pyproject.toml`. Версии заданы диапазонами; воспроизводимый lock-файл ещё нужно создать. Не использовать окружения соседних проектов. В DotAudio создана своя `.venv`.

## Текущая структура

```text
src/dotaudio/
  app.py          запуск Qt, аргументы CLI
  controller.py   мост QObject между QML и сервисами
  desktop.py      Windows hotkeys, целевое окно, Ctrl+V
  qml/MainMvp.qml, TranscriptEditor.qml  оболочка MVP и редактор сегментов
  capture.py      микрофон, loopback, прямой эфир через FFmpeg
  pipeline.py     буфер речи, ограниченная очередь, live-session
  engine.py       локальный/удалённый ASR, выбор устройства
  storage.py      SQLite: сессии, сегменты, настройки
  transcripts.py экспорт и сопоставление ключевых фраз
  server.py       необязательный FastAPI-сервис
tests/            проверки с подставными моделями/устройствами
deploy/           CPU Docker-заготовка, loopback-порт
docs/             продуктовый контекст и передача работы
```

## Поток данных

```text
Microphone / System audio / HTTP stream
  -> float32, mono, 16 kHz
  -> endpointing + bounded queue
  -> RecognitionConfig + Engine
       -> local faster-whisper
       -> optional HTTP server -> faster-whisper
  -> segments {start, end, text}
  -> SQLite + UI signal
       -> overlay / clipboard / editor / keyword events

Media file -> decoder / Engine -> same segment contract
```

Контракт сегмента: секунды от начала конкретного источника, не Unix-time; `start >= 0`, `end >= start`, конечные числа. Сохранённый сегмент получает `id` и `original_text`. Внешние форматы переводят секунды в SRT/VTT-таймкод на границе экспорта.

Далее для событий эфира добавить отдельно абсолютное время захвата и относительную позицию. Не вычислять время новости по моменту завершения медленной модели.

## Границы ответственности

- QML отвечает за представление, переходы и доступность. Там не должно быть SQL, HTTP и правил распознавания.
- Controller переводит пользовательские действия в вызовы сервисов. По мере роста разделить его на контроллеры сессий, истории и моделей; избегать одного класса на всё приложение.
- Capture выдаёт нормализованные аудиоблоки и ошибки. Не запускает Whisper и не обращается к UI напрямую.
- Pipeline управляет временем, очередью, отменой и backpressure. Не должен незаметно выбрасывать речевые фрагменты.
- Engine не зависит от Qt. Локальный и серверный режимы возвращают одинаковые сегменты.
- Storage сохраняет состояние независимо от видимости окна. Правки исходного и распознанного текста различаются.
- Desktop содержит платформенные вызовы. На неподдерживаемой ОС должен быть явный clipboard fallback.

## Потоки, отмена и производительность

Тяжёлые библиотеки импортировать лениво; скачивание модели и открытие аудиоустройства выполнять вне GUI thread. Сигналы в Qt доставляют результат в основной поток. Никогда не обновлять QML-объекты непосредственно из Python worker thread.

Нужны строгие состояния сессии и однократное событие завершения. `stop` должен дописать хвост аудио; `cancel` прекращает вычисление и запрещает вставку. Повторные stop/cancel должны быть безопасны. Закрытие программы - отдельный сценарий: остановить захват, дождаться освобождения ресурсов, сохранить состояние.

Cancellation нативного inference кооперативная. Python Event не прерывает произвольную CUDA-операцию мгновенно. Для гарантированного таймаута/изоляции падения рассмотреть отдельный процесс распознавания вместо daemon threads.

В MVP одна модель кешируется, inference сериализуется. Перед production проверить lock вокруг всего жизненного цикла модели, переключение профиля и отсутствие повторной выдачи сегментов при GPU fallback.

Для live нужен bounded buffer в двух местах: между устройством и endpointing, между endpointing и моделью. Ошибка переполнения должна попадать в состояние источника. Энергетический порог - черновой endpointing; для тихой речи и шумных залов рассмотреть VAD с адаптацией и перекрытиями.

## Хранение

SQLite хранит историю, сегменты и настройки локально. Стандартный каталог определяется platformdirs; `--data-dir` переопределяет его для проверок. Аудио микрофона в MVP не сохраняется. Импортированные файлы не копируются, в истории остаётся путь.

Далее: миграции схемы, recovery незавершённых сессий, отдельная таблица событий мониторинга, индексирование больших архивов, фоновые операции с БД и пагинация. В текущем controller обновление истории/сегментов синхронное; это точка для измерений и улучшения.

## Сервер и Timeweb

Первая полезная схема: Windows-клиент захватывает звук и показывает UI, сервер с GPU распознаёт. Это снимает вычислительную нагрузку с ноутбука, но добавляет передачу аудио, сетевую задержку и эксплуатацию сервера. У Timeweb есть предложения с GPU; конкретный тариф, доступность и стоимость в этой сессии не подбирались. [Timeweb Cloud](https://timeweb.cloud/services/cloud-servers).

Текущий сервер - отдельный малый HTTP-адаптер с `/health` и `/v1/transcribe`. Он обрабатывает один запрос за раз, ограничивает размер и длительность аудио. Это не публичная многопользовательская платформа: нет аккаунтов, прав на задачи, постоянной очереди и биллинга. Порт привязан к localhost; для личного удалённого использования возможен SSH-туннель.

Для многоканального production-режима: API заданий → ограниченная очередь → worker → progress/results; при необходимости SSE/WebSocket. В таком варианте обязательны владение задачей, отмена, квоты и восстановление после падения. Redis/PostgreSQL/S3 вводить только когда появится соответствующая нагрузка и сценарий, не переносить весь .звук в демо заранее.

## Подход к проверкам

Unit: таймкоды, нормализация речи, дедупликация перекрытий, пороги/границы буфера, маршрутизация результатов по session_id, поиск, экспорт, сохранение правок. Integration: подставные устройства/модели, остановка в каждом состоянии, переполнение очереди, HTTP limits и занятость.

Отдельно нужны реальные проверки: микрофон/loopback, CPU/GPU, длинные файлы, нестабильная сеть, вставка в разные окна, масштабирование, второй монитор, установка на чистой Windows. Fake-тест не доказывает качество Whisper или работоспособность WASAPI.

Рекомендуемый benchmark-артефакт: версия модели/runtime, CPU/GPU/RAM, параметры, длительность записи, WER/CER, cold/warm latency, RTF, peak RAM/VRAM. Не вставлять в README цифры из чужих тестов как результат DotAudio.
